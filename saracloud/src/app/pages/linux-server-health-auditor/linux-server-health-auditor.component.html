01 PROJECT OVERVIEW

Understanding the project

The Linux Server Health Auditor is a Bash-based system administration The Linux Server Health Auditor is a team-based system administration project designed to provide a simple and structured way to assess the health of a Linux server. It was built to make routine server monitoring more consistent, helping administrators gain a clearer view of system conditions and identify issues that may require attention.

02 THE PROBLEM

Why was it needed?

A Linux server can experience performance and availability issues when critical resources or services are not regularly monitored. High CPU or memory usage, limited disk space, network connectivity problems, excessive processes, or unexpected port conditions can affect the reliability of a system.

Relying on manual checks makes it harder to consistently monitor these conditions and maintain a clear record of what was happening on the server at a particular time.

The challenge was therefore to create a simple and repeatable way to check key areas of server health, identify abnormal conditions through defined thresholds, and produce structured results that could be recorded and reviewed.

03 THE SOLUTION

Automating Linux server health monitoring

Our team developed a Bash-based Linux Server Health Auditor to automate essential server health checks and provide a structured view of system conditions.

The auditor monitors six critical areas of a Linux server: CPU usage, memory usage, disk usage, network connectivity, running processes, and ports. Each metric is evaluated against defined thresholds and assigned one of three health statuses: OK, WARNING, or CRITICAL.

The results are generated in JSON format with timestamps, making the audit output structured, machine-readable, and suitable for further reporting, logging, and monitoring.

04 TECHNOLOGIES & TOOLS

The tools behind the auditor

Linux

The operating system environment where the health auditor runs and collects system-level information.

Bash

Used to automate the health checks, process system information, evaluate thresholds, and generate the audit results.

/proc/stat

Used by the script to access CPU-related information directly from the Linux kernel.

/proc/meminfo

Used to retrieve memory information from the Linux kernel.

df

Used to collect disk usage information from the Linux filesystem.

JSON

Used as the structured output format for timestamped health audit results.

Git & GitHub

Used for version control, collaboration, and managing the team's project repository.

Prometheus

Used locally to scrape the generated metrics and make them available for monitoring and dashboard visualization.

07 CHALLENGES & SOLUTIONS

What we encountered and how we solved it

Building the auditor as a team came with challenges that required us to test our approach, troubleshoot issues, and refine how the system handled and presented health-check information.

01
CHALLENGE

Working with raw system information

Collecting information directly from Linux system sources such as /proc/stat and /proc/meminfo produced raw values that were not immediately meaningful to users.

HOW WE SOLVED IT

We processed the collected values and structured the results into clear health-check output, making the information easier to interpret and use.

02
CHALLENGE

Keeping output consistent

With multiple system checks producing different types of information, maintaining a consistent structure across the results was important for both readability and further processing.

HOW WE SOLVED IT

We established a consistent output structure and used JSON for machine-readable results, allowing information from different checks to follow a predictable format.

03
CHALLENGE

Preserving audit history

A health check is more useful when its results can be reviewed after the script finishes. Relying only on terminal output would make previous audit results difficult to track.

HOW WE SOLVED IT

We implemented file-based logging with timestamps so that audit results could be stored and referenced later for review and troubleshooting.

04
CHALLENGE

Making results useful beyond the terminal

The auditor needed to produce results that could support both human review and integration with monitoring tools rather than being limited to terminal output.

HOW WE SOLVED IT

We separated human-readable reporting from machine-readable output and structured the results so they could also support the project's monitoring workflow with Prometheus.

05
CHALLENGE

Coordinating work across the team

Because different members were responsible for different parts of the auditor, keeping the components aligned was essential for producing a working and consistent final result.

HOW WE SOLVED IT

We divided responsibilities across the project and worked collaboratively to ensure that the health checks, reporting, logging, and monitoring components worked together as one system.
